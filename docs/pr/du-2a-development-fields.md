Base branch: `develop`. Depends on PR 1b (`feat/du-1b-scope-component`): this branch is cut from its tip, so retarget to `develop` once that PR merges. Branch: `feat/du-2a-development-fields`.

## Summary

PR 2a of `developments-units` (tasks 4.1 to 4.8, AD6 and decisions D1, D2, D3). It prepares the data and the rules for managing developments, with no screen yet (PR 2b): five optional profile fields, the archive state, the `developments.manage` permission, validation and the policy methods. Only the super-administrator may edit or archive a development; nobody deletes one.

## Database and row-level security

One migration, `20261120000001_AddDevelopmentProfileAndManagePermission`:

- `up()`: `ALTER TABLE developments` adds `address`, `phone`, `rfc`, `bank_name`, `bank_account` as `text NULL` and `archived_at` as `timestamp NULL`; inserts the permission `developments.manage` into `permissions`. No `role_permissions` row is inserted: RB-R4 resolves the super-administrator by role code, so it holds the permission without rows and every other role is refused.
- `down()`: deletes the permission (and any role rows pointing to it) and drops the six columns. It touches nothing else, unlike the catalogue seed (`20261118000001`), whose `down()` empties the whole catalogue.
- Row-level security: unchanged. The policies of `developments` are per row and the grant is per table, so the new columns are covered and only the super-administrator still writes (a new RLS test proves it for the new columns). `bank_account` is readable in SQL by every role that sees the development (coarse model accepted in the design); screens decide who sees it later.
- Tracked file `app/config/Migrations/schema-dump-migrations.lock` was regenerated by the migration run, as in the earlier migration PRs.
